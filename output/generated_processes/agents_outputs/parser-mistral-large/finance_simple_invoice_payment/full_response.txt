<bpmn_pseudocode>

```pseudocode
// Main Process: Vendor Payment Processing
messageStartEvent("InvoiceReceived")
  serviceTask("Log invoice into accounting system")
  scriptTask("Computation: calculate payment due date from invoice terms")

  // Scheduled sub-process for payment generation
  timerStartEvent("On calculated due date"):
    serviceTask("Generate payment request")
    userTask("Finance manager approves payment")
    serviceTask("Process payment via bank transfer")
    sendTask("Send: payment confirmation to vendor")
    endEvent("Payment process complete")
```

**TIMER VALIDATION**:
- `timerStartEvent("On calculated due date")` uses natural language but will map to:
  ```json
  {
    "$type": "bpmn:TimerEventDefinition",
    "timeDate": "{dueDate}"  // Dynamically calculated in prior scriptTask
  }
  ```
  - **Note**: This requires the due date to be stored as an ISO 8601 datetime variable from the script task. If the system cannot dynamically reference calculated dates, this would need to be refactored as a **recurring daily check** with a conditional start:

  timerStartEvent("Daily at 09:00"):

<critical_notes>
1. **Dynamic Due Date Handling**:
   The current design assumes the BPMN engine can reference a dynamically calculated due date in the timer event. If this is not supported, the process must be refactored to use a **daily recurring timer** with a conditional check (see alternative pseudocode above).

2. **Payment Approval Assumption**:
   The flow assumes approval is always granted. If rejection is possible, an `XOR` gateway would be required after the approval task.

3. **Error Handling**:
   No error boundaries added for bank transfer failures or approval timeouts, as these were not mentioned in requirements. These could be added if explicitly required.
</critical_notes>
