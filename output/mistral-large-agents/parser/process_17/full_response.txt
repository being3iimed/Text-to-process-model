### **1. Summary of Elements**

#### **TASKS**
- `userTask("Record Order Details")` - Manual entry of customer order
- `serviceTask("Process Payment")` - Automated payment gateway call
- `sendTask("Send: payment failure notification")` - Customer notification
- `serviceTask("Check Stock Availability")` - Inventory system query
- `sendTask("Send: back-order notification")` - Customer delay notice
- `receiveTask("Receive: back-order items")` - Wait for restock (no timerBoundary - no SLA mentioned)
- `serviceTask("Pick Items from Warehouse")` - Warehouse operation
- `serviceTask("Perform Quality Control")` - Inspection step
- `serviceTask("Package Items")` - Standard packaging
- `if (gift_wrap_requested): serviceTask("Add Gift Wrapping")` - Conditional task
- `serviceTask("Prepare Shipping Documents")` - Logistics prep
- `if (international_order): serviceTask("Prepare Customs Documentation")` - Conditional task
- `serviceTask("Dispatch Order")` - Handoff to carrier
- `sendTask("Send: shipping confirmation")` - Customer update
- `serviceTask("Update Inventory Levels")` - System update
- `sendTask("Send: feedback request")` - Post-delivery email
- `receiveTask("Receive: delivery confirmation")` - Carrier update
- `receiveTask("Receive: customer issue report")` - Trigger for returns (no timerBoundary - no SLA mentioned)

#### **GATEWAYS**
- **XOR** after payment processing (`success`/`failure`)
- **XOR** after stock check (`in_stock`/`back_order`)
- **XOR** after dispatch (`gift_wrap_requested` = binary)
- **XOR** after dispatch (`international_order` = binary)
- **XOR** after delivery confirmation (`issues_reported`/`no_issues`)

#### **EVENTS**
- `startEvent("Order Placed")` - Trigger: manual (customer action)
- `endEvent("Order Fulfillment Complete")` - Normal completion
- `endEvent("Payment Failed")` - Early termination
- `endEvent("Returns Process Complete")` - Subprocess completion

#### **BOUNDARY EVENTS**
- **None added**:
  - No explicit SLA/timeouts mentioned for any task.
  - No expected error scenarios described (e.g., "system crash during payment").
  - *Critical Compliance*: Boundary events are **only** added when explicitly justified by requirements.

#### **SUBPROCESSES**
- **Returns Process** (Justification: Cohesive 4-step workflow with clear purpose: "handle customer returns").
  - Passes **Three-Question Test**:
    1. Purpose: "Process customer-initiated returns from delivery issues."
    2. Tasks: 4 related steps (label → receive → inspect → refund/replace).
    3. Removal Impact: Would clutter main flow with tangential logic.

### **2. BPMN Pseudocode**
```pseudocode
startEvent("Order Placed")

// --- Order Recording & Payment ---
userTask("Record Order Details")
serviceTask("Process Payment")

if (payment_successful):
    // --- Inventory Check ---
    serviceTask("Check Stock Availability")

    if (items_in_stock):
        proceed_to_picking()
    else:
        sendTask("Send: back-order notification")
        receiveTask("Receive: back-order items")  // No timerBoundary (no SLA)
        proceed_to_picking()
    END_IF

    // --- Warehouse Operations ---
    subProcess("Fulfillment Preparation"):
        startEvent("Preparation Start")
        serviceTask("Pick Items from Warehouse")
        serviceTask("Perform Quality Control")

        // Gift Wrapping (Conditional)
        if (gift_wrap_requested):
            serviceTask("Add Gift Wrapping")
        END_IF

        serviceTask("Package Items")
        endEvent("Preparation Complete")
    endSubProcess

    // --- Shipping ---
    AND:
        serviceTask("Prepare Shipping Documents")

        if (international_order):
            serviceTask("Prepare Customs Documentation")
        END_IF
    END_AND

    serviceTask("Dispatch Order")
    sendTask("Send: shipping confirmation")

    // --- Post-Dispatch ---
    serviceTask("Update Inventory Levels")
    sendTask("Send: feedback request")
    receiveTask("Receive: delivery confirmation")

    // --- Returns Handling (Conditional) ---
    if (customer_reports_issues):
        subProcess("Returns Process"):
            startEvent("Return Initiated")
            sendTask("Send: return shipping label")
            receiveTask("Receive: returned items")
            serviceTask("Inspect Returned Items")

            if (refund_approved):
                serviceTask("Process Refund")
            else:
                serviceTask("Process Replacement")
            END_IF

            endEvent("Returns Process Complete")
        endSubProcess
    END_IF

    endEvent("Order Fulfillment Complete")

else:  // Payment Failed
    sendTask("Send: payment failure notification")
    endEvent("Payment Failed")
END_IF
```

### **4. Key Design Decisions**
1. **No Boundary Events**:
   - *Why*: Description lacked explicit SLAs (e.g., "payment must process in <2 hours") or expected errors (e.g., "API fails 5% of the time").
   - *Compliance*: Boundary events require **explicit justification** per BPMN spec.

2. **Returns as Subprocess**:
   - *Why*: Grouping 4 related tasks ("label → receive → inspect → refund/replace") improves readability and reusability.
   - *Validation*: Passes **Three-Question Test** (clear purpose, cohesive tasks, removal would clutter main flow).

3. **Parallel Shipping Docs**:
   - *Why*: "Prepare Shipping Documents" and "Prepare Customs Documentation" (if international) are independent.
   - *Compliance*: Uses `AND`/`END_AND` for true parallelism.

4. **Gift Wrapping Conditional**:
   - *Why*: Binary decision (`gift_wrap_requested`) mapped to `XOR` with 2 branches.

---
### **5. Assumptions**
- **Payment Retries**: Not mentioned → treated as single attempt.
- **Back-Order SLA**: Not specified → `receiveTask` has no `timerBoundary`.
- **Delivery Confirmation**: Assumed to come from carrier (no customer action required).
- **Feedback Email**: Sent immediately after `delivery confirmation` (no delay mentioned).
