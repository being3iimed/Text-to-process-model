```pseudocode
startEvent("IT Solution Request Submitted")

userTask("IT Assesses Request")
  description: "Check compatibility, cost, and resource needs"

if (approved):
    subProcess("Deploy Solution"):
        startEvent("Deployment Initiated")

        serviceTask("Procure Tools/Licenses")
        serviceTask("Install Solution")
        serviceTask("Test in Controlled Environment")

        if (test_successful):
            endEvent("Deployment Complete")
        else:
            userTask("Troubleshoot Installation Issues")
            endEvent("Deployment Failed")
    endSubProcess

    serviceTask("Roll Out to Department")

    if (training_required):
        userTask("Provide Training")
    end_if

    serviceTask("IT Support Available")
    endEvent("Request Fulfilled")

else:  // rejected
    sendTask("Send: Rejection Notice to Requester")
    endEvent("Request Rejected")
end_if
```

## **Structural Justifications**

### **1. Subprocess: "Deploy Solution"**
- **Why?**
  - Groups procurement, installation, and testing into a reusable unit.
  - Isolates complexity from the main flow.
  - Clear single responsibility: "Deploy and validate."

### **2. No Boundary Events**
- **Why?**
  - No explicit SLAs (e.g., "must respond within 24 hours").
  - No error scenarios mentioned (e.g., "if procurement fails").
  - **Avoids speculative design.**

### **3. Explicit Gateway Convergence**
- **XOR after assessment** → **Merged before "Roll Out"**
  - Ensures all paths reconverge cleanly.

### **4. Optional Training**
- **Modeled as conditional branch** (not a subprocess)
  - Keeps main flow linear for the common case.
