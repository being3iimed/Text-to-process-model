### **1. Summary of Elements**

#### **TASKS**
- `userTask("Record Order Details")` - Manual entry of customer order
- `serviceTask("Process Payment")` - Automated payment gateway call
- `sendTask("Send: payment failure notification")` - Customer notification
- `serviceTask("Check Stock Availability")` - Inventory system query
- `sendTask("Send: back-order notification")` - Customer delay notice
- `receiveTask("Receive: back-order items")` - Wait for restock (no timerBoundary - no SLA mentioned)
- `serviceTask("Pick Items from Warehouse")` - Warehouse operation
- `userTask("Perform Quality Control Checks")` - Manual inspection
- `serviceTask("Package Items")` - Automated packaging
- `serviceTask("Add Gift Wrapping (if requested)")` - Conditional packaging
- `serviceTask("Prepare Shipping Documents")` - Shipping dept. task
- `serviceTask("Prepare Customs Documentation")` - International orders only
- `serviceTask("Dispatch Order")` - Logistics handoff
- `sendTask("Send: shipping confirmation")` - Customer update
- `serviceTask("Update Inventory Levels")` - System update
- `sendTask("Send: feedback request")` - Post-delivery email
- `receiveTask("Receive: delivery confirmation")` - Wait for customer confirmation
- `userTask("Initiate Returns Process")` - Manual trigger if issues reported

#### **GATEWAYS**
- **XOR** after payment processing (`payment_successful` vs. `payment_failed`)
- **XOR** after stock check (`in_stock` vs. `out_of_stock`)
- **XOR** after packaging (`gift_wrapping_requested` vs. `no_gift_wrap`)
- **XOR** after shipping docs (`international_order` vs. `domestic_order`)
- **XOR** after delivery confirmation (`issues_reported` vs. `no_issues`)

#### **EVENTS**
- `startEvent("Order Placed")` - Trigger: Customer submission
- `endEvent("Order Fulfillment Complete")` - Normal completion
- `endEvent("Payment Failed")` - Early termination
- `endEvent("Returns Process Complete")` - Post-delivery path

#### **BOUNDARY EVENTS**
- **None** (No explicit SLAs or expected error scenarios mentioned)

#### **SUBPROCESSES**
- **Returns Process** (Justified: Cohesive 4-step workflow with clear purpose)
  - Purpose: Handle customer-reported delivery issues
  - Criteria: Passes Three-Question Test (3+ related tasks, single purpose, improves readability)

### **2. BPMN Pseudocode**

```pseudocode
startEvent("Order Placed")

// --- Order Recording ---
userTask("Record Order Details")

// --- Payment Processing ---
serviceTask("Process Payment")
if (payment_successful):
    // --- Inventory Check ---
    serviceTask("Check Stock Availability")
    if (in_stock):
        serviceTask("Pick Items from Warehouse")
        userTask("Perform Quality Control Checks")

        // --- Packaging ---
        serviceTask("Package Items")
        if (gift_wrapping_requested):
            serviceTask("Add Gift Wrapping (if requested)")

        // --- Shipping Preparation ---
        AND:
            serviceTask("Prepare Shipping Documents")
            if (international_order):
                serviceTask("Prepare Customs Documentation")
            END_IF
        END_AND

        // --- Dispatch ---
        serviceTask("Dispatch Order")
        sendTask("Send: shipping confirmation")
        serviceTask("Update Inventory Levels")

        // --- Post-Delivery ---
        sendTask("Send: feedback request")
        receiveTask("Receive: delivery confirmation")
        if (issues_reported):
            subProcess("Handle Returns"):
                startEvent("Returns Process Initiated")
                sendTask("Send: return shipping label")
                receiveTask("Receive: returned items")
                userTask("Inspect Returned Items")
                if (refund_approved):
                    serviceTask("Process Refund")
                else:
                    serviceTask("Process Replacement")
                END_IF
                endEvent("Returns Process Complete")
            endSubProcess
        else:
            endEvent("Order Fulfillment Complete")
        END_IF

    else: // Out of stock
        sendTask("Send: back-order notification")
        receiveTask("Receive: back-order items")
        // Rejoin main flow after restock
        serviceTask("Pick Items from Warehouse")
        userTask("Perform Quality Control Checks")
        // ... (rest of flow as above)
    END_IF

else: // Payment failed
    sendTask("Send: payment failure notification")
    endEvent("Payment Failed")
END_IF
```

### **4. Key Design Decisions**
1. **No Timer Boundary Events**:
   - `receiveTask("Receive: back-order items")` has no `timerBoundary` because no SLA was mentioned.
   - `receiveTask("Receive: delivery confirmation")` similarly lacks a timer, as no timeout was specified.

2. **Subprocess for Returns**:
   - Justified by the **Three-Question Test**:
     - **Q1**: "Handle customer-reported delivery issues" (clear purpose).
     - **Q2**: 4 related tasks (label, receive, inspect, refund/replace).
     - **Q3**: Removing it would clutter the main flow with edge-case logic.

3. **Parallel Gateway for Shipping Docs**:
   - `AND` gateway used for `Prepare Shipping Documents` + `Prepare Customs Documentation` (if international) to emphasize independence.

4. **Explicit Convergence**:
   - All `XOR` gateways (e.g., stock check, gift wrapping) have labeled merge points to avoid ambiguity.

5. **Minimal Boundary Events**:
   - None added because no **explicit** error scenarios (e.g., "API fails") or SLAs (e.g., "must ship in 2 hours") were mentioned.

---
### **5. Assumptions**
- **Gift Wrapping**: Assumed to be a binary choice (requested or not) with no partial wrapping.
- **Customs Docs**: Assumed to be required for all international orders (no exceptions).
- **Returns Process**: Assumed to be triggered only after delivery confirmation (not preemptively).
- **No Partial Shipments**: If an order has multiple items, all must be in stock to proceed (no partial fulfillment).
